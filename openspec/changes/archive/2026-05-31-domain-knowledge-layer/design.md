## Context

OpenSpec skills currently receive domain context only through a flat `context:` string in `config.yaml`. This is injected uniformly into every agent interaction with no structure, no selectivity, and no way to express relationships between concepts. It breaks down past ~200 words.

The goal is a layered knowledge system that scales to large domains while keeping per-interaction token costs low. All storage is file-based markdown to stay consistent with OpenSpec's existing conventions. No external infrastructure (vector databases, embedding APIs) is introduced.

## Goals / Non-Goals

**Goals:**
- Token-efficient retrieval: minimal tokens loaded by default, concept files on demand
- Two-tier knowledge: static (curated upfront) and discovered (captured during development)
- Skill-scaffolded: `/opsx:domain` interviews the user or reads existing code to draft the initial KB
- Convention-based activation: `openspec/domain/` presence enables all domain awareness
- Index always current: auto-regenerated at archive time, never hand-maintained
- Consistent terminology: skills use domain vocabulary when naming code, specs, and proposals

**Non-Goals:**
- Semantic/vector search — too heavy a dependency; name-based lookup is sufficient
- Domain knowledge versioning beyond a `status` field on discoveries
- Automatic extraction without user confirmation
- Enforcing domain constraints (advisory only, not blocking)

## Decisions

### 1. YAML index over markdown index

**Decision**: `_index.yaml` (structured YAML) rather than `_index.md` (markdown table or prose).

**Rationale**: YAML is ~3× more token-efficient than equivalent markdown prose for structured data. A 30-concept domain fits in ~600-800 tokens as YAML vs ~2,000 tokens as prose. Since the index is loaded on every skill invocation, this compounds significantly.

**Alternative considered**: Markdown table — better human readability, but worse token density and harder to parse programmatically.

### 2. Convention over config

**Decision**: `openspec/domain/` directory presence enables domain awareness. No `config.yaml` changes needed.

**Rationale**: Consistent with how OpenSpec already works (changes directory, specs directory). Zero-friction adoption — create the directory and it works. Projects that don't need domain knowledge are unaffected.

**Alternative considered**: Opt-in via `config.yaml` `domain.enabled: true` — explicit but adds setup friction.

### 3. Archive as the index sync trigger

**Decision**: `_index.yaml` is regenerated by `/opsx:archive` before the change is archived. Manual sync via `/opsx:domain sync` also available.

**Rationale**: Archive is the natural boundary between changes. The index is always current at the start of new work (propose/explore begins after an archive). Direct file edits during development are allowed; they're swept into the index at archive time.

**Alternative considered**: Regenerate on every skill invocation — always fresh but adds read overhead to every interaction.

### 4. Two-layer concept files (frontmatter + prose body)

**Decision**: Each concept file has machine-readable YAML frontmatter and a human-readable prose body. Skills choose which layer to read.

**Rationale**: Frontmatter contains the structured facts that cover ~80% of queries (name, aliases, related concepts, states, rules). Prose body is only read when depth is needed (implementation phase). This minimizes token cost for proposal/explore phases.

**Structure**:
```
---
name: Invoice
type: concept
aliases: [bill, billing-doc]
related: [Customer, Payment, LineItem]
states: [draft, pending, approved, paid, disputed]
rules: [approved-before-payment]
---
Full prose definition, edge cases, examples...
```

### 5. Discovered knowledge as separate files with provenance

**Decision**: Discovered knowledge lives in `openspec/domain/discovered/` as separate files, not appended to static concept files.

**Rationale**: Discoveries have a lifecycle (active → superseded → invalidated) that static concepts don't. Keeping them separate allows the index to surface their status clearly without polluting static content.

**Frontmatter fields**:
```yaml
name: invoice-disputed-state
type: discovery
discovered_in: add-invoice-dispute-flow
date: 2026-05-31
relates_to: [Invoice]
status: active  # active | superseded | invalidated
superseded_by: null
```

### 6. Load order: index always → concept files by name → body only when implementing

**Decision**: Skills follow a strict load order to minimize tokens:
1. `_index.yaml` — always loaded when `openspec/domain/` exists
2. Specific concept files — loaded only when their name appears in the current change/task scope
3. Prose body — read only during implementation (apply), not during proposal/explore

## Risks / Trade-offs

- **Index drift** → Mitigation: archive always regenerates; `domain sync` available for mid-development use
- **Large domains (100+ concepts)** → Mitigation: YAML keeps the index compact; if index exceeds ~2,000 tokens, `domain add` warns the user
- **Skill adoption burden** → Mitigation: each skill gets clear, specific instructions for when/what to load; the protocol is mechanical, not inferential
- **Discovery staleness** → Mitigation: `status` field on discoveries; archive skill flags `superseded` discoveries when newer changes contradict them
- **Scaffolding quality** → Mitigation: `/opsx:domain init` shows drafts before writing and asks for confirmation; users can always edit files directly

## Migration Plan

1. No changes to existing changes or specs — purely additive
2. `openspec/domain/` is opt-in by presence; existing projects unaffected until they create it
3. Skills updated in sequence: `domain` skill first, then `archive`, then `explore`/`propose`/`apply`
4. Teams adopt by running `/opsx:domain init` on any existing project

## Open Questions

- Should `/opsx:domain init` have a code-first mode (read existing codebase and infer concepts) or always be conversation-first? Currently scoped as conversation-first with optional codebase reading.
- Maximum recommended index size (token budget) — suggest defining a soft warning threshold during implementation.
